## 2. 选定方案与不变量

```text
用户点击导出
  → loadIndex：固定有序 ID、封面、摘要统计与 revision R
  → 逐条 readVisit(id, expectedRevision=R)
  → 既有 v2 NDJSON 编码、逐卷 UTF-8/SHA-256
  → 每卷写入独立 IndexedDB 导出暂存并等待提交
  → 清单完整 + 逐卷校验/包装计数 + 最后 assertRevision(R)
  → 导出会话 ready（只表示本机副本生成完毕）
  → 用户选择一卷 → 校验/包装该卷 → 一个活动下载 Blob URL
```

约束：

1. 主库维持 schema 4，导出对主库只读。只新增 `assertRevision` 方法，不为导出增加主库表、不递增主库 revision。
2. 新独立导出暂存库 schema 1，只有 `sessions/parts` 两个 store。暂存不进入正式记录、导入会话或公开发布包。
3. source revision、暂存 session ID、archive ID、导出时间均固定，不在中途混用新旧库内容。发现版本变化、缺行或内容不合规就失败，不跳过记录来凑齐备份。
4. 处理一条记录后释放它，只允许一个活动来源读取；编码器最多持有一个活动 payload 缓冲，写完一卷并等待事务结束才继续。不能以 `Promise.all(ids.map(readVisit))` 重建全库。
5. 会话清单与各卷摘要可留在内存，完整 payload/Blob 不组成数组；UI 最多持有一个活动导出下载 Blob URL。可见照片组件或分享卡的独立 URL 不算在导出计数中，应分开测量。
6. 取消、配额不足或暂存不可用不悄悄回退到旧整库 RAM 路径，也不引导先删除重要回忆。只清理明确导出 session，原库、其他导出和导入会话不变。
7. 不上传资料或私人照片、不增加收费依赖；使用 IndexedDB、Blob、TextEncoder、现有 SHA-256 和普通下载链接，不依赖 File System Access、目录授权或 OPFS。

这里的“磁盘 spool”指浏览器管理的 IndexedDB 持久暂存；不承诺浏览器完全不用 RAM，也不承诺设备故障后永久保留。

## 3. 一致性边界

### 固定版本 R 的快照，而非一直锁住主库

`loadIndex()` 已在同一事务核对摘要数量、封面引用与库版本。取结果后复制有序 ID、封面和所需元数据，固定 `exportedAt`、记录/照片/地点统计、日期范围；不保留无关 UI 响应式对象。

逐条调用 `readVisit(id,{expectedRevision:R,signal})`。返回 null、非法记录或 revision 不同均终止。每条完整记录的白名单投影还要与固定摘要核对，实际累计数量、日期范围和照片顺序必须与开始时一致；不能只相信初始计数。末尾新增 `assertRevision(R,{signal})`，在只读事务中只读取 `libraryMeta`，并等待事务完成。

全部来源读取均核对 R，最后检查覆盖了“最后一条读完后、生成清单前另一页改变封面或记录”的窗口。若另一页在最终检查之后修改主库，已生成的副本仍是有效的 R 时刻快照，**不宣称 ready 时仍是最新库**。主库与暂存库之间没有跨库原子事务；正确性来自固定内容和最终校验，而非虚构跨库锁。

`assertRevision` 不得通过再次 `load()` 实现，也不需要重读全部摘要。现有正式写入事务维护 revision；绕开应用手工篡改 IndexedDB 且不更新 revision 的行为不在这一版本机制的保证范围。摘要结构/统计/引用校验和暂存哈希仍需要执行。

### 已完成副本与后续下载

ready 后主库可继续变化，不再因此作废这一完整备份。重新下载 ready 会话复用其 archive ID、导出时间和字节；“重新生成最新备份”创建新 session 和 archive ID，不能把新卷混进旧清单。

取消发生在最后校验与 ready 之间时，仍不得发布 ready。通过会话状态/写入 token 的 CAS 拒绝迟到完成；如果 ready 已经提交，后续取消应描述为“清理已生成临时副本”，不是“撤销主库写入”。

## 4. v2 兼容编码与逐卷暂存

### 不改变现有线格式

当前 v2 为 `format:'shanhai-backup-volume', version:2`，payload 编码为 `shanhai-ndjson-v1`，每行均以换行结束，顺序必须保持：

1. 一行 `{kind:'library', visits, photos, covers}`。
2. 每条回忆一行 `{kind:'visit', value:...}`，其中 `photos` 只有 `id/name`；随后按原顺序输出该回忆所有 `{kind:'photo', visitId, photoId, url}` 行。
3. 全部回忆之后才输出 `{kind:'cover', value:...}`。

`manifest.records = 1 + visits + photos + covers`。清单字段保持 `encoding, summary, covers, records, parts`；每个 part 元数据保持 `{bytes,sha256}`。`archiveSha256` 必须由既有 `manifestText` 的规范字段顺序计算。每卷顶层字段仍为 `format, version, archiveId, exportedAt, parts, part, archiveSha256, payload`，仅第 1 卷带 `manifest`；导出 session ID、revision、临时状态不得泄漏为额外顶层字段，否则旧恢复器会拒绝。

现有默认 `VOLUME_CHARS = 16 * 1024 * 1024` 是字符预算，不是 UTF-8 字节预算。保留“不拆开 UTF-16 代理对”的分割规则，每卷独立计算 UTF-8 字节数与 SHA-256；记录可以跨卷，不能擅自按一条 Visit 一个 JSON 文件代替。每个最终 JSON 包装文件还要独立校验不超过既有 100 MiB；payload 长度、清单大小、JSON 转义开销和最终文件长度不能混算。

现有私有帮助函数应从同一权威 codec 内复用/提取出受测试的 sink 编码接口，再机械同步到 Vue。不要在新服务复制另一份标准化、SHA、序列化顺序或 v2 协议实现。WebCrypto 不可用时保留既有可让出执行权的 SHA-256 后备，不要求安全上下文才可本机导出。

### 为什么必须先 spool，再提供下载

第 1 卷包含完整 parts 列表及清单哈希，生成第一份 payload 时还不知道后续卷数和校验值。因此先将 payload 逐卷存入 parts，收齐小型元数据后生成 manifest/archiveSha256，再公布下载入口；不能提前下载“不完整第一卷”并让用户后续自行替换。

建议 parts 中保存独立 payload Blob（精确 UTF-8）及摘要，避免意外保留对巨大来源字符串的切片引用。完成时逐卷核对存储摘要/文件数，逐卷包装并验证最终文件大小以计算准确 totalBytes；这遍不留全部成品 Blob，也不生成下载 URL。下载所选卷时再读取一卷、复核 bytes/hash、按固定清单包装为文件 Blob。读写、哈希、包装都按串行背压执行。

单条照片 JSON 行和一个 Visit 仍可能很大。需要先释放上一卷字符串、编码字节和哈希输入，再继续下一卷；不能在异步闭包、进度记录或错误对象里附上完整照片对象。

## 5. 新暂存库、状态与接口

### 已实现的持久化模型

生产暂存库由 `travel-services.ts` 显式命名为 `${dbName}-exports-v1`，默认 `shanhai-lijiang-local-v1-exports-v1`；测试注入独立名称。名字中的 v1 与主库 schema 4、备份格式 v2 互不相同。

| Store | 主键 | 字段与职责 |
| --- | --- | --- |
| `sessions` | `id` | sourceDbName、sourceRevision、createdAt、状态、私有 writerToken/cleanupToken、nextPart；ready 保存 archive（ID/时间/manifest/hash）、轻量文件元数据、summary 与 totalBytes，不含整库照片 |
| `parts` | `[sessionId,part]` | 单卷 payload Blob、UTF-8 bytes、sha256；按 session 范围游标读取/清理，不用全库 `getAll()` |

状态为 `building → ready → deleting → 删除完成`，失败/取消进入 deleting；清理失败保留明确的 cleanupPending。只有 ready 可读取下载卷。在 id/sourceDbName 可确认时，损坏元数据公开为 `damaged` 安全投影，仍能显示并指定清理，不成为下载许可；身份也损坏则拒绝读取，不猜测清理目标。building 不自动续写，用户可清理重建，完整 ready 可继续下载。

每个写入事务必须同时核对 session 存在、building 状态及 writerToken；`appendPart` 不得在 session 被清理后自动重建它。ready 转换需核对实际卷数、索引连续性、摘要和统计，不把进度计数当作落盘依据。只有 `transaction.oncomplete` 才报告写入完成。

私有 writer token 不进入公开 ready/list 描述符；自动取消/失败清理在置 deleting 和删除 parts 两阶段均验证 token，随机 ID 碰撞或他人重新使用 ID 不会误清已有会话。ready 提交后仍保留私有所有权供本次取消清理使用；明确用户清理与自动失败清理的授权范围不同。

跨页清理一个仍在生成的 session 时，先显式告知会终止该份生成并确认；以事务将其置 deleting 并使 token 失效，再按该 session 清理 parts，最后删除 session。其他页的迟到写入或 `complete` 会被 CAS 拒绝。不能仅凭时间戳把可能仍在运行的 session 当作已停止，也不自动扫描删除其他会话。


## 6. UI 与隐私

- 生成过程显示“正在准备第 N 条 / 正在暂存第 N 卷 / 正在核对”，未知总卷数时不编造百分比；准备期间可取消，不自动下载一套尚未 ready 的分卷。
- ready 列表只保留文件名、part、bytes、requested 等轻量信息；卷很多时分页/滚动展示元数据，不为列表显示读取 payload。
- 用户先“准备这一卷”，生成唯一活动链接，再由真实点击触发下载，避免异步读完后自动点击在手机上失去用户激活。切换卷前撤销上一 URL，清空旧 Blob 引用；同一卷失败可重试。
- 点击下载仅记“已发起”，不自动删除该卷、标记系统落盘或宣布整套已备份。保留重新下载；用户确认保管完成后可清理临时副本。
- 原生浏览器没有可靠的下载完成事件；不要在 anchor 点击回调中立即 revoke。活动 URL 可保留到准备下一卷、显式清理或卸载，正确性须做真实文件往返验收。
- 组件卸载/切换会话取消当前读取、阻止迟到 URL，撤销已有 URL；ready 的持久副本可稍后明确继续或清理，building 尽力取消清理，无法清理时下次可见提示。
- 新增提示：“生成备份需要额外本机临时空间。临时副本未加密，含照片与手记；下载并确认保管后可以清理。”`navigator.storage.estimate()` 只作提示，不证明写入必定成功；不自动请求永久存储授权。
- 不记录照片 URL、手记正文或完整备份到日志；不发送遥测，不上传云端，不为此接入收费服务。临时库与同来源数据共享浏览器配额，清理网站数据仍可能同时损失正式回忆与临时副本。

## 7. 取消、失败与重试规则

| 时刻/异常 | 应执行 | 不允许 |
| --- | --- | --- |
| 来源读取/版本变化/缺行/非法内容 | 终止本次生成，清理指定 session，保留原库；用户重新生成最新快照 | 跳过异常行、自动混合新 revision、降级 `load()` |
| 哈希或包装中取消 | 停止后续工作，等待无法中断的在途操作结算，再清理并释放引用 | 新请求立即叠加旧大缓冲，或迟到哈希回调继续写入 |
| parts 写入中取消/配额不足 | 等事务 abort/complete 的真实结果；使 session token 失效后清理本 session | 以 UI Promise 提前拒绝代替真实事务终止 |
| 最后校验与 ready 竞态 | 检查信号与 session CAS；只报告实际 ready 提交结果 | 取消后迟到生成下载入口，或把已提交 ready 谎报“从未生成” |
| 清理失败 | 留 cleanupPending、具体 session 与重试按钮，原库不变 | 清空整个暂存库、删除其他人的/其他页的 session |
| 页面关闭/崩溃后遗留 | 显式列出元数据；ready 校验后可续下，building 需清理重建 | 自动续读已改变的原库并拼接旧卷 |
| 下载卷缺失/损坏 | 阻止该卷下载并标明副本不完整，允许清理或重新生成 | 用当前主库临时补一卷塞进旧 archive |
| 用户重试下载 | 从同一 ready session 读同一卷，保持文件名/内容 | 重建 archive ID 造成混卷 |

不可取消的 WebCrypto digest 只计算字节但仍占内存；取消实现必须跟踪其底层结算，不把外层 Promise 的拒绝当作资源已经释放。需防重复开始和跨会话迟到完成；无需把整个主库持久事务锁在跨卷哈希期间。

## 8. 小库 v1 与资源预算

当前正常交互导出统一使用磁盘暂存 v2；既有 v1 读取/恢复、旧 `serialize/prepareExport` 兼容入口和历史测试保持。小库 v1 快捷路径尚未实施：后续候选预算为 **累计规范化内容不超过 8 MiB 且不超过 128 条**，这些仍是待测建议，不是生效限制或用户可保存容量上限，也不能替代 v1 原有 100 MiB/2000 条格式边界。

小库判定也从索引与逐条读取开始，使用精确字节计数，不能先 `load()` 完整图库才决定它太大。累计达到预算即改走同一 R 的 spool v2，将已有有限前缀按顺序写出并释放；任何版本变化仍整次失败。不得缓存超预算完整快照，也不得为了让 v1 成功截断记录或要求删照片。若这一分支让首轮风险过高，可先提供稳定 v2，待独立预算测试完成再接 v1 快捷路径。

需要分别度量：全库摘要/ID 与 parts 清单元数据、最多一条含图 Visit、单张照片 JSON 行、一个卷的编码/哈希/包装工作集、一个活动下载 Blob。清除全库峰值不等于清除单条或单张峰值；9 张各 10 MiB 图片的 Visit 加 base64/校验/序列化副本仍很重，后续照片分表是另一项迁移，不在本阶段偷改 schema 或压缩原有备份照片。
