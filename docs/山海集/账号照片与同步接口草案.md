## 1. 已完成的本机首轮与后续闭环

本机首轮已完成限定验收：测试账号A → 四川自定义地点 → 一张服务端去EXIF的合成照片 → 回忆/地图封面 → 第二会话读取元数据并按需看图 → CAS冲突 → 删除墓碑 → B不能访问A对象。证据为14项真实PG/HTTP测试、14组独立HTTP、5个VM场景与5190桌面QA/重启，分别记账；不代表真机、正式Vue或公网同步产品完成。

当前使用显式本机alice/bob测试身份、真实PostgreSQL和私有本机文件，只签发测试会话；不是内存mock，也没有生产短信、真实用户资料或付费存储。私有云桶适配器尚未实现，后续需保留现有签名权限、不可变代次、隔离暂存、退休先提交及可重试回收语义。

会话读取、地点创建、上传prepare/complete/状态、回忆增改删与元数据列表、封面设置、私有签名读取、变更拉取和收据查询均已有本机API，Vue核心接通另有独立验收。下一安全工程优先持久固定快照/显式断点迁移，并行可维护公共目录；真实身份、私有云存储、部署和费用需要用户选择。快照/迁移须在接入真实旧库前完成，账号注销生命周期须在正式账号服务前明确。

当前 `remote` 适配器与 `LocalRepository` 分离，通过TravelServices接入App；独立 `shanhai-account-v1-<UUID>` schema1持久保存cache/draft/outbox，界面区分已读取、同步中、待处理与冲突。结果未知不等于未提交，先查原收据再重试。账号草稿仅留本浏览器，退出/重启后可恢复，不成为云草稿；普通本机仍沿用 `expectedVersion` CAS。5190历史QA的内存行为不能代表此实现，完整离线首次登录/迁移仍未交付。

## 2. 数据关系与服务端不变量

当前服务端主键使用 `crypto.randomUUID()` 的随机UUID，公共地点ID是公开业务身份；随机ID不能替代权限检查。实际SQL私人实体的归属列名为 `owner`，逻辑契约称 `owner_account_id`，均只从验证会话确定；请求体额外的 `userId/ownerAccountId` 返回 `400 INVALID_FIELD`。下表为逻辑设计与落地映射，不是可直接执行的DDL；权威表结构见 [001_initial.sql](../../shanhai-api/migrations/001_initial.sql)。

| 表 / 资源 | 核心字段 | 约束 |
| --- | --- | --- |
| `account` | `id, auth_subject, status, created_at, sync_epoch` | 身份提供方与 subject 组合唯一；关闭账号使会话与新上传失效 |
| `custom_place` | `id, owner_account_id, name, region_id, longitude, latitude, validation_version, version, deleted_at` | 地点元数据不可原位改变；改名/移位创建新身份，原记录保持引用 |
| `visit` | `id, owner_account_id, place_kind, public_place_id?, custom_place_id?, date, note, cover_photo_id?, client_created_at, created_at, updated_at, version, deleted_at` | public/custom 二选一；内部封面须属于该回忆；同日同地允许多条，须产品确认而非数据库唯一约束 |
| `photo` | `id, owner_account_id, visit_id?, state, object_key, input_sha256, stored_sha256, bytes, width, height, mime, safe_name, version, deleted_at` | 上传就绪前不得挂到回忆；就绪后最多属于一条回忆；对象 key 不来自客户端 |
| `visit_photo` | `owner_account_id, visit_id, photo_id, position` | 顺序唯一；photo 与 visit 同属一个账号；每条最多 9 图 |
| `map_cover` | `owner_account_id, place_key, visit_id, photo_id, version, deleted_at` | 每账号每地点唯一；必须指向该地点某条有效回忆中的有效照片 |
| `upload_session` | `id, owner_account_id, photo_id, object_generation, expires_at, expected_bytes, expected_sha256, state` | 只可写指定隔离暂存对象；重签名或重传不覆盖已验证正式对象 |
| `sync_change` | `owner_account_id, sequence, entity_type, entity_id, entity_version, operation, payload` | 与业务写入/墓碑同事务提交；保存对应版本快照，不能事后拼当前值 |
| `mutation_receipt` | `owner_account_id, operation_id, request_hash, result, created_at` | 幂等键和结果与业务变更同事务写入；相同键不同请求拒绝 |
| `migration_session/item` | `owner_account_id, source_library_id, local_id, entity_type, request_hash, remote_id, status` | 本机迁移的断点映射与收据；同一 localId 不静默吞掉不同内容 |

实际已有 `accounts/sessions/custom_places/visits/photos/uploads/map_covers/sync_commits/mutation_receipts/download_grants/cleanup_tasks` 及服务签名密钥表。部分逻辑字段保存在JSONB `data`；有序照片引用保存在 `visits.data.photos`，目前没有独立 `visit_photo` 表。`migration_session/item`、生产提供方身份字段及下文固定快照表仍为后续设计，不能按上表声称已建表。

私人关联使用包含 `owner_account_id` 的复合外键或等效事务校验，避免只检查“这个 ID 存在”。`map_cover` 还要验证 `visit.place_key == map_cover.place_key`。删除回忆时，关联照片与该条所承担的地图封面一并进入删除状态并产生同步事件。

后续迁移要求服务端ID与本机 `visit-…/custom-…/photo-…` 分开，使用拟议侧表 `(accountId, sourceLibraryId, entityType, localId) → remoteId, remoteVersion`；该完整迁移映射尚未实现，不重写旧身份。当前API序号/版本已用十进制字符串，日期保留用户 `YYYY-MM-DD` 并以上海时区今天校验；同步按服务端sequence排序，客户端时间不决定提交顺序。

## 3. 会话、请求规则与错误格式

当前本机实现为12小时 `HttpOnly; SameSite=Strict` 会话Cookie，只有显式HTTP loopback测试模式不设Secure；业务写入校验CSRF和精确Origin，不启用宽泛CORS。生产后续必须使用HTTPS/Secure与受支持的授权码流程，校验state、nonce、PKCE、回调地址、签发方、受众和期限；真实身份/OIDC尚未实现。身份认证不能替代业务授权，长效凭证不放localStorage。

| 端点 | 请求 | 成功返回 |
| --- | --- | --- |
| `POST /api/v1/testing/login`（本机已实现） | `{subject:"alice"或"bob",secret}`，精确Origin；不把秘密写入bundle | 200，测试会话、account、csrfToken、expiresAt |
| `GET /api/v1/auth/login`（拟议，未实现） | 已登记的 provider 与应用内 returnTo；禁止任意外部跳转 | 302 到身份认证流程 |
| `GET /api/v1/auth/callback`（拟议，未实现） | code、state；由服务器校验交换 | 设置会话并 303 返回应用 |
| `GET /api/v1/session` | Cookie | `200 {account:{id,status},csrfToken,expiresAt}` |
| `POST /api/v1/auth/logout` | CSRF；空 body | 204，撤销当前会话 |

除登录外，当前私人端点每次验证有效账号、会话及对象归属，包括签名 URL 签发、上传完成和业务收据查询。未来后台照片任务和迁移收据也必须携带数据库确认的 owner 与对象代次，不信任客户端任意 object key；不能据此声称这些未来任务已实现。跨账号与不存在对象统一返回 404，避免透露对象是否存在；系统内部审计可区分原因。

当前业务变更使用 `Idempotency-Key`；测试登录/退出、按需download-url及能力PUT/GET有各自认证/一次性语义，不产生普通业务收据。回忆/地点的语义更新和删除要求 `If-Match: "<version>"`，地图封面首建用If-None-Match，更新/删除用If-Match；上传取消由状态/引用约束，不要求该版本头。方法、路径、前置版本和规范正文组成请求hash。同键同内容重放原结果、异内容409；丢响应后查收据或用原键重试，不换键盲目新增。

```json
{
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "这条回忆已在另一端更新，本机修改仍保留。",
    "requestId": "<trace-id>",
    "details": { "resourceId": "<owned-id>", "currentVersion": "8" }
  }
}
```

| HTTP / code | 行为 |
| --- | --- |
| 400 `INVALID_FIELD` / 422 `VALIDATION_FAILED` | 返回允许展示的字段错误；无业务写入 |
| 401 `SESSION_EXPIRED` | 当前适配器停止请求并隐藏私人树，保留独立账号草稿/outbox，重新登录后显式继续；不清匿名库 |
| 404 `NOT_FOUND` | 不存在或不属于当前账号；不回传他人元数据 |
| 412 `VERSION_CONFLICT` / 409 `IDEMPOTENCY_CONFLICT` | 保留本机副本；读取当前自有资源并显式处理 |
| 410 `RESOURCE_DELETED` / `PHOTO_RETIRED` | 已删除身份不自动复活；`CURSOR_EXPIRED`与快照重建是后续保留期设计 |
| 413 `PHOTO_TOO_LARGE` / `PHOTO_QUOTA`，415 `CONTENT_TYPE_MISMATCH` | 保留本机照片；不挂接不合格对象，不删除旧回忆腾空间 |
| 422 `INVALID_PHOTO` / `IMAGE_DECODE_FAILED` / `PHOTO_NOT_READY` | 返回实际失败原因；未ready对象不可读 |
| 428 `VERSION_REQUIRED` | 补读版本后再提交，不绕过并发控制 |
| 429 `BUSY` / `LOGIN_RATE_LIMIT` | 限制传输/转换或登录；当前无507账户配额契约，照片预算使用413 |
| 503 `OBJECT_READ_UNAVAILABLE` | 暂存读取暂错，保持uploaded、无失败收据，可重试完成操作 |

当前限制为每条9图、输入/输出各10MiB、手记2000字符、地点名1–60字符、最多40MP解码/最长边2400像素JPEG；转换5秒、HTTP请求15秒、传输/转换各最多2并发。每账号最多500个占用身份、100MiB保守对象预算（输入预留+实际输出+待清理对象），不是无限照片容量。能力接口目前公开单图/每条上限，其他值以README/源码为准，不声称所有限制已由capabilities返回。

## 4. 私有照片上传、校验与读取

当前本机服务端保存实际sharp解码/重编码副本，默认去除EXIF等元数据；不能信任前端Canvas已经清理。仅允许实际JPEG/PNG/WebP单页，拒绝伪装格式和超限输入，不修改原文件。私有云存储尚未实现，不能把当前本机对象目录称为云备份。

```text
prepare → 受限签名上传到私有隔离对象 → complete → 服务端验证/重编码
                                               ↓ ready
                            保存回忆事务挂接 photo → 按需签名读取
```

`POST /api/v1/photos/uploads`，携带幂等键：

```json
{ "clientPhotoId": "photo-local-1", "name": "旅行.jpg", "contentType": "image/jpeg", "bytes": 12345, "sha256": "<input-64-hex>" }
```

返回 `201`：

```json
{
  "uploadId": "<random-upload-id>", "photoId": "<random-photo-id>", "state": "prepared",
  "upload": { "method": "PUT", "url": "<short-lived-signed-url>", "headers": { "Content-Type": "image/jpeg" }, "expiresAt": "<UTC-time>", "maxBytes": 10485760 }
}
```

当前签名绑定用途、对象、账户、会话、代次及5分钟期限；上传先核会话，再核持久令牌hash/状态与实际长度/hash，不允许客户端指定路径/ACL/桶名。暂存为私有本机文件，无公开永久链接；签名URL不进入日志或change。每次请求重核会话可阻止退出后的新请求，但不能撤回已开始传输/已另存的字节；未来直签云桶须重新说明撤销延迟。

上传后 `POST /api/v1/photos/uploads/{uploadId}/complete` 使用原流程对应的独立幂等键，body 为 `{}`。服务器读取其登记的对象代次，核对实际大小与 SHA-256，真实解码、重编码，生成受控正式 key。客户端 ETag、MIME、字节数和“上传成功”都不能替代服务端检查。固定对象版本或复制到内部不可变 key 后再验证，防止验证完成前后被重传替换。

当前同步完成返回 `200 {photo:{id,state:"ready",inputSha256,storedSha256,bytes,width,height,mime,version},receipt}`；没有202异步validating任务。状态查询实际为prepared/uploaded/ready/rejected/cancelled/expired。重编码的storedSha256可不同于输入；后续迁移须使用身份映射和变换收据对账，不能当作丢图。

幂等complete重试返回同一photo。`POST /api/v1/photos/uploads/{uploadId}/renew`仍为拟议，当前没有续期；过期上传需取消后以新clientPhotoId建立新代次。DELETE只能取消未挂接照片。已上传未完成/未挂接ready对象有24小时宽限，需显式清理调用；不自动后台回收，已有有效回忆引用的对象不得被删除。

当前 `POST /api/v1/photos/{photoId}/download-url` 验证ready/自有/已挂接有效回忆，返回 `200 {url,expiresAt,mime,bytes,sha256}`，有效期60秒。签名GET经API逐次重核会话、grant和对象，响应private/no-store；退出可阻止该会话后续新读取，不能追回已下载或正在传输副本。未来云直签需另验撤销策略，不能套用当前代理读取结论。

当前连接适配器不持久化上传/下载URL；按需下载后核对JPEG长度/SHA，映射成现有组件的data URL。关闭、取消或身份失效会终止请求并卸载私人树；已另存副本不能追回。API同步摘要只有照片元数据；账号草稿与未确认outbox仍可含输入照片，完成操作清除输入。日志不记照片、手记、秘密或URL查询令牌；不做跨账号哈希去重。

## 5. 地点、回忆与地图封面 REST 契约

`POST /api/v1/custom-places` 请求：

```json
{ "clientId": "custom-local-1", "name": "成都的小茶馆", "regionId": "cn-51", "coordinates": [104.0665, 30.5728], "validationVersion": "<published-boundary-version>" }
```

返回 `201 {customPlace:{id,name,regionId,coordinates,validationVersion,version:"1"}}`。服务器由 regionId 推导省区，按固定规则验证，不信任客户端省份标签。未知验证版本返回 `422 VALIDATION_VERSION_UNSUPPORTED`，附当前能力版本，保留草稿。`GET /api/v1/custom-places/{id}` 只返回自己的地点；改名/改归属/移位用新 POST 取得新身份，再 CAS 更新特定回忆的引用，不波及其他回忆。没有有效引用的自定义点可用带 If-Match 的 DELETE 删除；仍被引用返回 409。

`POST /api/v1/visits` 请求：

```json
{
  "clientId": "visit-local-1", "clientCreatedAt": 1788739200000,
  "place": { "kind": "custom", "id": "<owned-custom-place-id>" },
  "date": "2026-09-07", "note": "雨天喝茶",
  "photos": [{ "id": "<owned-ready-photo-id>", "position": 0 }],
  "coverPhotoId": "<owned-ready-photo-id>"
}
```

公共地点引用为 `{kind:"public",id:"yulong",catalogueVersion:"<version>"}`。旧公共点 ID 保持稳定；私人快照策略遵从全国数据契约。示例时间只表示毫秒字段类型，不充当校验日期或业务证据。

成功返回 `201 {visit:{id,...,version:"1"},changeSequence:"<decimal-sequence>",receipt:{operationId,replayed:false}}`，同时返回 `ETag: "1"`。地点引用、照片归属及就绪状态、图数、封面从属和版本在一个事务内核对并提交；该事务同步建立摘要、维护照片关系与 change 事件。成功仅代表这条回忆已经提交，上传暂存清理失败单独记录，不把整个保存重报为失败。

| 端点 | 返回 / 事务语义 |
| --- | --- |
| `GET /api/v1/visits?cursor=…&limit=50` | `{items:[VisitSummary],nextCursor,snapshotVersion}`；无照片字节；最大100条，库变化后旧列表cursor返回409 `STALE_LIST`并重新列举，不是持久固定快照 |
| `GET /api/v1/visits/{id}` | 当前自有回忆详情、元数据和 ETag；照片仍按需获取 URL |
| `PATCH /api/v1/visits/{id}` | If-Match 与幂等键；字段白名单，替换 photos 数组时整体校验；返回新 version |
| `DELETE /api/v1/visits/{id}` | If-Match 与幂等键；原子写 visit/photo/map_cover 墓碑，返回删除版本及操作收据 |
| `GET /api/v1/map-covers` | 当前账号有效精选关系列表；没有照片字节 |
| `PUT /api/v1/map-covers/{placeKey}` | `{visitId,photoId}`；已存在需 If-Match，首建需 If-None-Match:*；返回 version |
| `DELETE /api/v1/map-covers/{placeKey}` | If-Match；只删除该用户的精选关系，不删除照片 |
| `GET /api/v1/mutations/{operationId}` | 当前账号自己的已提交结果或 404；用于断线后判断提交结果 |
| `GET /api/v1/capabilities` | 当前返回API/目录/验证版本、34省区/49region/43公共点、`completeNationalCatalogue:false`、`testIdentityOnly:true`、单图/单条限制和去元数据能力；`fixedSnapshots:false`、`legacyMigration:false`，不返回完整配额/墓碑策略 |

`placeKey` 使用 `public:<stablePlaceId>` 或 `custom:<remoteCustomId>` 的规范化结果，按 URI 编码传递，服务器解析并重新校验，不作为任意路径。`coverPhotoId` 是一条回忆内部封面，`map_cover` 是地图上该地点跨回忆的精选封面，两者独立。删除内部封面照片时显式选择剩余封面或清空；引用失效的地图封面同步清空，不暗中指向另一个地点的照片。

## 6. 同步 cursor、版本、幂等与冲突

当前服务端按账号分配单调 `sequence`，业务与change原子提交；cursor不透明、绑定账号/epoch，不以客户端时钟替代。同一事务的多实体变化使用相同commit且不拆页。Vue适配器已在一个账号IndexedDB事务中应用完整提交与cursor，未知字段/不连续序列拒绝且不推进；受控事务测试见 [适配器说明](../../shanhai-app/qa/vue-integration-20260907/REMOTE.md)，不能说全部半页失败排列都做过原生验收。

增量接口为 `GET /api/v1/sync/changes?cursor=<opaque>&limit=100`：

```json
{
  "commits": [{ "id": "<commit-id>", "sequence": "8", "changes": [
    { "entity": "visit", "id": "<visit-id>", "version": "8", "operation": "upsert", "value": { "note": "另一端的修改" } }
  ] }],
  "nextCursor": "<opaque>", "hasMore": false
}
```

例子 `value` 为精简说明，实际协议需返回该版本完整允许同步字段，不能只给补丁而没有基准。事件含有该版本的快照，不能读到第 8 版事件却拼入第 9 版数据。删除事件只带身份、版本和 deletedAt，避免保留可读照片正文。分页错误不推进本地 cursor；重放同一页按版本幂等应用。

以下固定快照流程仍为拟议、尚未实现（当前 `fixedSnapshots:false`）：首次登录或 cursor 过期时，`POST /api/v1/sync/snapshots` 创建固定视图，返回 `{snapshotId,throughCursor,expiresAt}`；`GET /api/v1/sync/snapshots/{id}/items?cursor=…` 分页返回自有资源摘要；下载完成后，在隔离暂存库中核对完整性，再原子切换该账号的云镜像并从 throughCursor 拉增量。服务端需 MVCC 固定视图或物化快照，不能将多次普通列表请求当作一致快照。拟议过期返回410并重建，但须保留未上传 outbox 与冲突副本；当前测试期变更未自动到期。

当前outbox按账号库隔离，实际字段为 `id/digest/target/kind/status/createdAt/payload/expected/steps/result/error`；保存前持久记录原输入、CAS基准和操作键，按自定义地点→ready照片→visit依赖执行，map_cover独立操作。步骤进度写回后可查询原收据恢复，退出停止当前实例但不删除队列；不是后台无限自动重试。pending/conflict/done/discarded有不同语义，结果未知时不能丢弃后悄悄继续发送；已完成结果保留收据并清除输入照片。不要声称每次草稿编辑都和入队同事务：草稿CAS与提交入队是独立边界。

本轮修复的原子边界是“同一草稿明确另存新visitId时，保存新草稿并归档旧目标terminal conflict”；有结果未知pending则拒绝换身份，错误CAS/其他草稿目标不能归档。最终原生恢复旧删除冲突草稿后明确另存新visit/photo，刷新无孤立pending；原visit仍410、原photo新授权404，新图真实解码。关闭编辑器会自动刷新摘要，避免继续展示另页已删记录。619项历史的持续丢响应/重启实验与630项最终修复分开记录。

冲突处理首版不自动最后写入获胜，也不自动按字段合并。412 版本冲突时保存本机候选与服务器最新副本；用户可保留云端、基于新版本确认覆盖，或另存新回忆。每种选择形成新的明确操作 ID。云端已经删除的记录与本机待上传编辑冲突时，显示删除事实；旧操作不能自动创建相同身份的记录，用户可将本机内容另存为新回忆。

当前测试期永久保留 change、收据和墓碑，没有自动压缩/到期。正式保留期设计要求收据期限不短于最长有效重试窗口；未来迁移收据与删除身份防复活标记不能随普通上传缓存清理。墓碑至少90天是待确认建议，不是当前上线策略；未来落后超过保留窗口的cursor需410并固定快照重建。实体ID不复用，现有已删clientId映射保留；正式到期清理还须保留最小删除身份标记或等效机制，防止旧请求复活对象。

## 7. 首次本机迁移与断点（拟议，未实现）

登录不自动上传匿名本机库。先读取不含照片字节的索引，显示记录数/照片数/草稿不上传，并由用户选择具体库和目标账号。这个明确选择才建立迁移授权；后续断点继续绑定同一账号、来源库与清单，不扩大到其他浏览器来源。

本机来源库生成持久随机 `sourceLibraryId`，它是同步侧表字段，旧 v1/v2 备份本身没有此身份。不同来源恢复同一备份后不能仅凭日期/地点或照片 hash 自动判为同一库；需要预览可能重复项，保守处理同 ID 不同内容。

| 端点 | 请求 / 返回 |
| --- | --- |
| `POST /api/v1/migrations` | `{sourceLibraryId,localRevision,counts,manifestHash}` → `201 {migrationId,state:"staging"}` |
| `GET /api/v1/migrations/{id}` | 已完成项、失败项、各项 remoteId、最近收据；分页返回明细 |
| `POST /api/v1/migrations/{id}/items` | 有界批次的身份/内容哈希与已就绪照片引用；逐项原子提交并返回收据，不能夹带整库 Base64 |
| `POST /api/v1/migrations/{id}/complete` | 清单对账 → `{state:"complete",counts,manifestHash}`；存在缺项/冲突则 409 |
| `POST /api/v1/migrations/{id}/cancel` | 停止未开始项并清理仅属该会话的无引用暂存；返回已提交项数量 |

逐条读取时沿用 `readVisit(id,{expectedRevision})` 的本机版本栅栏。源库变化使当前计划 stale，暂停并重新核对，不混合两个版本声明完整迁移。上传并发和工作集有界，照片逐张传输并确认；单条回忆的照片全 ready 后再保存，不收集整库 `Visit[]`。

云迁移与本机备份恢复的提交范围不同：当前备份导入的正式合并是整次原子；拟议云迁移按回忆原子并提供可恢复的部分成功清单。取消云迁移不会自动删除此前已提交的云回忆，必须显示实际数量，不能宣称整库回滚。照片暂存清理不得删除已挂接对象。重新开始同一来源迁移复用收据；同一 localId 不同内容返回冲突并要求明确处理。

迁移 complete 后不自动清空本机库。先核对摘要、封面关系、每张照片状态、随机或完整下载校验和第二端恢复结果，再由用户决定是否移除该设备的副本。合法服务端重编码可能改变字节，但必须保存输入/输出校验收据，且图数、顺序、名称、手记、地点与封面可对账。

当前账号隔离已实现：外壳接收跨页登录变化并重核会话，失效时取消请求、卸载整棵私人UI/照片/卡片/编辑器；账号IndexedDB/cache/outbox/cursor彼此隔离，迟到响应落地前核对实例身份，匿名库独立。最终原生验证多页看图时退出清私人树以及A/B/普通本机模式不串资料；全部上传中切账号/晚到排列未全原生覆盖。未来迁移会话与后台任务也须按账号隔离；私人响应不得进入共享Service Worker缓存。

## 8. 安全删除、回收与备份边界

当前删除回忆先做带版本和幂等键的逻辑删除：数据库事务中记录 visit/photo/map_cover 墓碑并取消可读关系。持久清理任务先提交退休状态，再独立执行具体 key/generation 的物理删除与确认；每阶段重核引用，失败可重试，不通配删除整个用户目录。当前由 `POST /api/v1/cleanup/retry` 显式驱动，`GET /api/v1/cleanup-tasks` 查看自有状态，没有后台定时执行器。删除未提交时保留原记录，已提交但回收失败时应报告“已删除，服务端文件清理中”，不把记录复活；这不是云文件已清理的证明。

当前未引用自定义地点通过带版本的显式DELETE删除，没有自动延后清理策略或服务端restore端点。若后续提供撤销删除，须明确可恢复窗口与独立CAS restore，并在回收前保留数据；不能借用现有本机撤销按钮承诺撤回服务端删除。当前没有云回收站。

删除账号独立使用近期重新认证和显式确认：拟议 `POST /api/v1/account-deletions` 建立有收据的删除任务，先撤销会话/新上传，再删除业务数据、暂存对象及关联派生图；后台工作可检查 `GET /api/v1/account-deletions/{id}` 的受控状态。真正启用前必须规定账号删除后的状态查询凭据、不可逆点、保留时限、失败重试与审计记录，未实现这些环节时端点不能暴露为“已永久删除”。

短签名 URL、已经下载的照片、用户自己导出的私人备份与隔离存储的服务运维备份有各自生命周期。服务端删除不撤回用户已下载的文件；运维备份的保留与到期清除需单独披露并验证。不能承诺点击删除后所有历史副本即时消失。

现有 `shanhai-backup` v1 与分卷 v2 是用户可持有的时间点副本，校验和不提供加密或作者认证，草稿不包含在其中。云同步会传播修改和删除，不是防误删的离线备份。首版继续保留手动导出/导入；备份恢复仍先预检、实际图片解码、暂存预览，再确认提交。同 ID 不同内容拒绝覆盖，当前地图封面优先；云冲突解决不能偷换现有本机导入语义。

将来从云库生成 v1/v2 备份时先创建版本固定的导出任务，按需获取真实照片字节并增量写卷，不能把会过期的签名 URL 写进备份当作照片。账号退出、版本变化或下载失败时保留错误与可清理暂存，不产生标为完整的缺图备份。

## 9. 实现顺序与验收矩阵

本机API和5192实际Vue核心接通/恢复已限定验收，不再列为待开始。下一安全工程优先持久固定快照/明确授权迁移，并行可维护公共目录；真实身份、私有云存储和正式账号生命周期另立门槛，提供方/域名/HTTPS/部署与费用需要用户选择。每一步保持统一错误格式与owner约束。

| 编号 | 必测场景 | 通过标准 |
| --- | --- | --- |
| B01 | A/B 两账号猜到对方 visit/photo/custom/upload/receipt ID | 所有读取、关联、complete 和签名接口拒绝；无对象存在性或内容泄漏 |
| B02 | 请求体伪造 userId，上传伪造 MIME/长度/hash/图片头 | 不接受 owner；实际对象校验失败，不能挂到回忆 |
| B03 | complete 后重传同 key、重复 complete、任务重启 | 读取的是固定对象代次；同 photo 一次 ready；无已验对象被覆盖 |
| B04 | A 的 photo 挂到 B 的 visit，错误地点/错误回忆当 map_cover | 同事务拒绝，业务表/摘要/change 日志均无部分提交 |
